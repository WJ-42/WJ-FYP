1. Introduction and Motivation

Large language models are now highly capable at individual software engineering sub-tasks: writing code, following instructions, producing designs, analysing data. But almost all existing tools treat this as a single conversation with a single assistant. That is not how software is actually built. A working system is produced by a team: product managers scoping work, engineers implementing it, testers verifying it, all communicating and iterating together, often with disagreement, rework, and escalation along the way. There is no accessible tool that tests whether a coordinated team of specialised LLM agents, each modelled on a distinct role in a real software company, can take a high-level requirement and autonomously turn it into a working, tested system.

This project investigates that gap directly. Rather than building a single, more capable coding agent, it builds an organisation of agents, a virtual software company, and studies how well that organisation performs the earliest and most expensive stage of software delivery: turning an ambiguous requirement into a working, verified product.

1.1 Business and research relevance

For a solo developer, small team, or research group, on-demand access to a full engineering department without hiring or coordinating one has direct commercial relevance for solo founders, agencies, and product teams. The project also sits inside active multi-agent LLM research: it engages with the growing literature on how role structure, communication design, and personality affect the output quality of orchestrated LLM teams, and it deliberately builds on an existing failure taxonomy (Cemri et al.'s MAST framework) rather than inventing failure categories from scratch.

The project does not aim to compete with industry-scale tools such as ChatDev or MetaGPT, nor does it treat formal repeated experimentation as its primary deliverable. The priority is a strong, functioning system whose design decisions can be explained and defended individually. Function comes before visual polish, and every architectural choice is made for a stated, defensible reason.

1.2 Related work

Three papers assigned as supervisor-directed background reading each map onto a specific design decision in this project, in some places confirming the chosen approach and in others motivating a deliberate departure from it.

Generative agent architectures

Park et al. (2023) demonstrate that believable, emergent social behaviour in simulated agents arises from three components: a natural-language memory stream recording every experience, a reflection layer that periodically synthesises those memories into higher-level insights, and a planning process that retrieves both when deciding what to do next. Starting from a single seed constraint, their agents autonomously organise a party, spreading invitations and coordinating attendance without being scripted to do so. This is evidence that memory, reflection, and planning are jointly necessary for believable social behaviour, since ablating any one of them degrades it.

This project deliberately does not adopt the full memory-and-reflection architecture. Where Park et al.'s agents pursue open-ended social goals with no fixed completion criterion, this project's agents work against concrete, checkable units of work: tickets with explicit acceptance criteria and, where available, hidden tests. That difference in task structure is what justifies replacing a persistent per-agent autobiographical memory with the lighter structured handoff note passed at each transition (Section 4.3.5): sufficient context to complete a bounded task, at a fraction of the token cost a full memory-and-reflection cycle would add if run on every one of the potentially hundreds of tickets processed during evaluation. This is a considered trade-off given the project's explicit cost constraint (Section 8), not an omission. It also directly motivates measuring "context lost at handoff" as its own failure category (Section 6.3), since the lighter mechanism is the one place this project's design most obviously trades fidelity for cost relative to the generative-agents architecture.

Role-specialised multi-agent simulation

Li et al. (2024) simulate a hospital in which every patient, nurse, and doctor is an LLM-powered agent, with doctor agents improving over tens of thousands of simulated patient encounters and, once evolved, outperforming prior state-of-the-art medical agents on the external MedQA benchmark.

The role-specialisation pattern and the strategy of validating the system against an external, published benchmark rather than a bespoke one both carry over directly to this project's design (Section 4 and Section 6.5, respectively, the latter through TheAgentCompany). Where this project departs is on agent evolution: Agent Hospital's doctor agents accumulate experience and change behaviour over repeated encounters, whereas this project's agents use fixed, tiered models per role for the full duration of any evaluation run. That choice follows from a difference in evaluation goal. This project aims to characterise a fixed architecture's failure modes (Section 6.3) and compare it against a single-agent baseline (Section 6.4), which requires the architecture under test to stay constant across runs rather than improve mid-evaluation. Agent evolution of this kind is a plausible direction for future work rather than current scope.

Staged pipelines with human-in-the-loop feedback

Schmidgall et al. (2025) structure autonomous research assistance as a staged pipeline (literature review, experimentation, then report writing) with a human able to give feedback at each stage boundary, and report that this human involvement measurably improves output quality. The same paper reports an 84% reduction in cost relative to prior autonomous research systems, achieved partly through deliberate model selection at each stage rather than using one model throughout.

Both findings map closely onto decisions already made here. The staged pipeline with feedback at defined boundaries is structurally the same pattern as this project's ticket finite-state-machine with intervention gated at specific transitions (Sections 4.3.4 and 4.6): human oversight inserted at defined points in a pipeline, rather than continuous supervision or none at all. The cost-efficiency result reinforces, rather than originates, the project's own tiered model allocation strategy (Section 7): cheaper models for high-volume Engineering-tier work, a stronger model reserved for CTO-tier architectural decisions.

2. Objectives

  1. Design and build a multi-agent orchestration system in which agents playing distinct organisational roles (CTO, Product, Engineering) turn a high-level requirement into a working software product.
  2. Support both attaching to an existing code repository and creating a new one, through a single unified code path.
  3. Design a communication protocol (message format, routing, turn-taking, context passing) that is simultaneously cheap to run, easy to defend architecturally, and rich enough to reconstruct the full decision-making process after the fact.
  4. Build a safe, isolated code execution sandbox so agent-generated code can be run and tested without risk to the host system.
  5. Allow the user to observe the multi-agent "company" at work in real time, and to intervene at meaningful decision points rather than only after the fact.
  6. Allow the user to extend the organisation itself by creating custom roles and personalities beyond the default preset team.
  7. Evaluate the resulting system's functional correctness, process efficiency, and failure modes against a single-agent baseline at a matched token budget.

3. System Overview

The deliverable is a tool that lets a user act as the CEO of a virtual software company. The user supplies a high-level requirement and either attaches an existing repository or has a new one created. Both flow through the same underlying ticket-generation pipeline, so there is one code path, not two parallel modes. A preset team of LLM agents across three organisational tiers, CTO, Product, and Engineering (which includes the tester role), takes the requirement, communicates over channels, breaks the work into tickets, implements, tests, and iterates. The user can also define custom roles and personalities and assign agents to them, so the organisation is not locked to one fixed structure. Two built-in views let the user observe and, where appropriate, intervene: a live chat/log feed of agent communication, and a kanban board tracking tickets from backlog through to done.

The role system is deliberately built for upgradability: role count, tier structure, and per-role model assignment are read from configuration (a RoleConfig schema), not hardcoded, so additional roles or tiers can be added later without reworking the core orchestration logic. This same mechanism is also what powers the user-facing custom role and personality feature described in Section 4.5.

4. Architecture

4.1 Core structural principle: one event log, many views

The single most load-bearing architectural decision in the system is that the message bus, the audit/event log, and every presentation surface (chat feed, kanban board, observability panels) are all views over the same append-only stream of typed Message records, not three separate systems that must be kept in sync. Every agent communication, every ticket state transition, and every sandbox tool call is logged as the same kind of record. This gives process metrics (message counts, rework loops, wall-clock time, token cost) "for free" from the log, without separate instrumentation, and it means the presentation layer can change completely without touching the orchestration core.

4.2 Repository handling

Whether the user attaches an existing repository or requests a new one, both paths converge on the same ticket-generation pipeline (Section 4.4). An empty new repository supports clean demonstrations; an existing repository with real tickets and hidden test suites is what enables genuine pass/fail evaluation, in the style of benchmarks such as SWE-bench or TheAgentCompany.

4.3 Communication protocol

4.3.1 Message schema

Every event in the system, agent chatter, ticket transitions, and sandbox tool activity alike, is represented as a single typed record:

Message {
  id: UUID
  timestamp: datetime
  sender: AgentRef            { role: str, instance_id: str }
  channel_id: str
  recipient: AgentRef | null  # optional direct address within a channel
  type: MessageType           # see below
  ticket_ref: str | null
  content: {
    text: str
    artifacts: [ArtifactRef]  # diff hash, file path, test report id, etc.
    handoff: HandoffNote | null
  }
  parent_id: UUID | null       # threading
  token_cost: { prompt: int, completion: int } | null
}

HandoffNote { done: str, remaining: str, notes_for_next: str }

MessageType = status_update | question | handoff | code_submission
            | review_feedback | escalation | tool_call | tool_result | system

Sandbox actions (running tests, writing files, committing) are logged as tool_call/tool_result messages in this same stream, rather than through a separate side-channel, so agent communication and code execution activity are reconstructable from one unified record.

4.3.2 Channels and grouping strategy

A channel is deliberately minimal: an opaque identifier plus a grouping key ({id, key}). The grouping semantics, whether by ticket, by feature, or by role, are not baked into the schema; they are a configuration choice exposed to the user. This means the system supports role-based channels (agents grouped by organisational function), feature-based channels (agents grouped by the area of the product they are touching), and ticket-based channels (one channel per unit of work, auto-created at ticket intake and closed on completion or halt) as interchangeable, user-selectable strategies rather than one hardcoded default.

4.3.3 Routing model

Agents never call each other directly. Three routing models were considered: direct orchestrator-to-agent calls, a shared bus/channel model, and a fully reactive shared task board that agents watch and act on autonomously. Direct calls were rejected as too tightly coupled and hard to log or defend; a fully reactive task board was rejected as the hardest of the three to control and debug. The system instead uses an orchestrator-mediated publish/subscribe model: the orchestrator invokes an agent with a constructed context payload, the agent's only output is a Message published to a channel, and the orchestrator reads channel and ticket state to decide who acts next. This keeps the underlying data structures identical to what a more autonomous routing strategy would use, so the routing policy can be upgraded later without a schema rewrite.

4.3.5 Context passing and handoffs

Replaying full raw message history at every agent invocation is both expensive and often irrelevant, and it obscures exactly the failure mode this project wants to be able to measure: context lost at a handoff. Every transition-triggering message must therefore include a structured HandoffNote (what was done, what remains, what the next agent needs to know). The next agent's actual context at invocation is: ticket metadata and acceptance criteria, the latest relevant artifacts by reference (not the whole repository tree), and the previous agent's handoff note, not raw channel history. A get_channel_history(n) tool is available for an agent to pull more context if it judges the handoff insufficient, which also gives a direct, measurable way to operationalise "context lost at handoff" as an evaluation variable: degrade or withhold the handoff note and measure the resulting downstream failure rate.

4.4 Execution sandbox

4.4.1 Isolation and granularity

Agents need to write and run code safely, without a bad generation being able to affect the host system. The sandbox runs one Docker container per ticket attempt, spun up when an Engineering agent needs to execute code for a specific ticket, and torn down after that attempt regardless of outcome. This bounds the blast radius of any single execution to one attempt and keeps resource usage and cost directly attributable per ticket. Containers run as a non-root user, without privileged mode, under CPU/memory/process-count limits and a hard execution timeout, with no network egress by default. Dependencies are baked into the base image, and a controlled proxy would only be introduced if an agent genuinely needed to install something at run time.

4.4.2 Tool interface

Agents are not given raw shell access. A fixed tool set, executed by a sandbox controller inside the container and returning structured results, is exposed instead:

run_tests()                 -> { passed, failed, output }
run_command(cmd)            -> { exit_code, stdout, stderr }
read_file(path)              -> content
write_file(path, content)
git_diff()
git_commit(message)

This mirrors the shape of standard LLM tool-use/function-calling, so it composes naturally with the underlying model API, and, consistent with Section 4.1, every tool call and result is logged as a message in the same unified event stream as agent communication.

4.4.3 Persistent workspace and git integration

Sandbox containers are ephemeral by design, but git history must persist across attempts and across tickets. A persistent per-run repository workspace sits beneath the ephemeral sandbox layer: each per-attempt container checks out from this persistent clone and pushes its commits back into it, so the container itself is fully disposable while the repository's history is not. Git usage follows one branch per ticket, with Engineering committing at each attempt; the Review → Done transition in the ticket state machine genuinely is the merge to the main branch, which makes CTO approval a real, consequential gate rather than a status label.

To preserve evaluation validity, the run_tests() tool available to agents only ever runs public/example tests bundled with a ticket. Hidden acceptance test suites, the ones used to score functional correctness (Section 6.1), are never exposed inside an agent's sandbox; they are run separately by the evaluation harness once a ticket reaches Review or Done.

4.5 Custom roles and personalities

Beyond the preset three-tier team, users can define their own roles, assign a personality to a role (a description of its behavioural tendencies that shapes its system prompt), choose which model powers it, and assign agents to it. This is implemented as an extension of the same RoleConfig schema that defines the preset roles, distinguished by an is_preset flag, so custom roles are first-class citizens of the same configuration mechanism rather than a bolted-on separate system.

4.6 Autonomy and human intervention

The system supports two operating modes. Autonomous mode runs a ticket end to end without any human input, which is necessary for unattended batch evaluation runs where hundreds of tickets may be processed for metrics collection. Intervention mode pauses the state machine at specific gating transitions and waits for a human approve/reject/redirect signal before continuing. The gating transitions are: Review → Done (final merge approval), Review → In Progress (requesting changes), Escalated → In Progress (CTO override after repeated failure), and Escalated → Halted (CTO gives up). These four transitions were chosen because they correspond exactly to the two ticket states where a human is most likely to want a say, Review and Escalated: approving what is about to be merged, and deciding how to handle a ticket the agent team could not resolve on its own.

4.7 Failure handling and escalation

The In Progress ↔ Awaiting Test loop is capped at three attempts. On the fourth failed test cycle, the ticket is force-transitioned to Escalated rather than looping again, handing it to the CTO agent. If the CTO's own resolution attempt also fails, the ticket moves to Halted and is logged with a MAST-style failure category (Section 6.3) at the moment of the failure, rather than being reconstructed after the fact from raw logs.

5. Observability and User Interface

The presentation layer was deliberately designed last, after the underlying event log was already presentation-agnostic. A pixel-art "walk around the virtual office" visualisation was considered and rejected as premature and unnecessary before the core system works. The interface serves two purposes simultaneously and with equal weight: it must let the user verify the tool is functioning correctly, and it must make the organisational dynamics of the simulated software company, decision-making, handoffs, escalation, collaboration, genuinely visible, since demonstrating a believable multi-agent society is as central to the project as the tool's technical correctness.

5.1 Dashboard and live updates

A web dashboard connects to the orchestrator over WebSockets and renders the event stream as it happens, rather than only after a run completes. This was a deliberate choice over passive after-the-fact log inspection: seeing agents deliberate, hand off, and occasionally fail in real time is a core part of what the project needs to demonstrate.

5.2 Chat/message feed

The default, always-visible view is a chronological chat-style feed of the message stream: sender, channel, message type, and any linked artifacts. It is deliberately kept minimal by default so the interface is not cluttered on first use.

5.3 Kanban board

A kanban board is the second built-in view, presented as a separate tab from the chat feed. It maps directly onto ticket status values as columns (Backlog, Specd, In Progress, Awaiting Test, Review, Done, Escalated, Halted), reusing the ticket data model rather than introducing a parallel one. Clicking a ticket card drills down into that ticket's channel and message thread, the same interaction pattern found in conventional issue trackers. The board remains meaningful even though only one ticket is ever actively being worked at a time (Section 4.3.4), since it shows the state of the entire backlog, not just the active ticket.

Intervention controls (Section 4.6) live directly on kanban cards at the two gating states: a card in Review shows Approve / Request Changes actions, and a card in Escalated shows CTO override options. This ties each control directly to the ticket state it affects.

5.4 Dual observability model

A settings panel exposes two independent groups of optional detail, on top of the always-visible chat feed and kanban board, so the interface can be tuned toward either purpose without needing two separate tools.

6. Evaluation Methodology

6.1 Functional correctness

Each ticket is scored against a hidden test suite, run by the evaluation harness rather than exposed to the agents, structured the same way as SWE-bench: a FAIL_TO_PASS set of tests that must flip from failing to passing (proving the ticket's requirement was actually implemented) plus a PASS_TO_PASS set that must remain passing throughout (proving no regression was introduced). Any install or test-harness failure on the evaluation side scores the ticket attempt as a hard failure rather than a partial pass, keeping the correctness signal unambiguous.

6.2 Process metrics

Because the event log already contains every message, tool call, and transition, process metrics are derived directly from it rather than requiring separate instrumentation: message counts per ticket, number of rework loops (re-entries into the In Progress ↔ Awaiting Test cycle), wall-clock time per ticket and per run, and token cost (prompt and completion, per message and cumulative).

6.3 Failure taxonomy

Run failures, escalations and halts, are categorised at the point of occurrence directly against Cemri et al.'s published MAST (Multi-Agent System failure Taxonomy) codes, rather than an approximated classification invented for this project. MAST defines 14 failure modes across three categories: Specification Issues (including code FM-1.4, loss of conversation history, the exact code for what this project calls "context lost at a handoff," directly measurable via the handoff-note mechanism in Section 4.3.5), Inter-Agent Misalignment (including failure to ask for clarification and reasoning-action mismatch), and Task Verification (including premature termination and incomplete verification). The specific tagging mechanism (rule-based, LLM-judged, or a mix) is an implementation detail decided at build time rather than fixed here; what is fixed is that whatever mechanism is used classifies against these 14 published codes rather than an invented taxonomy.

6.4 Baseline comparison

The same ticket is additionally run through a single agent operating alone at a matched token budget, to test whether the multi-agent structure earns its added complexity. This baseline deliberately reuses the identical Message/Ticket/sandbox infrastructure, with one agent instance playing all organisational roles in sequence, rather than requiring a second system to be built and maintained.

6.5 Benchmark strategy

Rather than writing custom test repositories and hidden tickets entirely from scratch, the evaluation harness adapts task material from TheAgentCompany (Xu et al., 2024). TheAgentCompany's full benchmark runs against a self-hosted service environment (GitLab, a project-management tool, team chat, and a file-storage service, each as a Docker image with pre-populated data). Standing up that entire environment was considered and deliberately rejected as disproportionate infrastructure for this project relative to the orchestrator, sandbox, and dashboard already being built, and it is not necessary for this project's evaluation goals, which are about the multi-agent architecture rather than benchmark-leaderboard comparability. Instead, this project takes just the task definitions from TheAgentCompany's Software Engineering category (69 of its 175 total tasks) and re-implements scoring checkpoints against this project's own ticket and git model rather than their service stack. Their scoring approach is adopted directly: partial credit rather than binary pass/fail, computed as score = 0.5 · (completed_checkpoints / total_checkpoints) + 0.5 · full_completion, where full_completion is 1 only if the ticket is fully resolved. This trades direct numeric comparability to TheAgentCompany's own published baseline figures for a much smaller infrastructure footprint, which was judged the right trade given this project's priorities.

8. Constraints and Risk Management

  • API cost. Running full multi-agent cycles repeatedly for development and evaluation is token-expensive. Mitigated by tiered model allocation (cheap models for bulk Engineering-tier work, a stronger model reserved for CTO-tier architectural decisions) and by the retry cap (Section 4.7) bounding how many cycles any single ticket can consume before escalating.
  • Sandbox safety. Considered the single trickiest technical component of the project: agent-generated code must be able to execute without risk to the host. Addressed through the per-attempt container isolation model in Section 4.4.1: non-root execution, no privileged mode, resource limits, no network egress by default, and full teardown after each attempt.
  • Explainability for the viva. The student has historically found it difficult to deeply internalise AI-generated code even when it has been explained. Because the orchestration loop, sandbox, and communication/routing system form the technical spine of this project and must be defended individually in the viva, not merely demonstrated as working, every architectural decision in this document is accompanied by the reasoning and rejected alternatives behind it, not just the chosen design.
  • Scope alignment. The technical design was checked against the submitted CS3IP Project Definition Form to ensure the two remain consistent; divergences found (channel grouping strategy, the custom roles/personalities feature, the kanban board, and human intervention) were resolved by aligning the working design to the form rather than the reverse, since the form's committed language was found to be correct in each case.

9. Expected Contribution

The project's primary contribution is a working proof point for whether an orchestrated team of role-specialised LLM agents can compress the earliest, most expensive stage of software delivery, turning an ambiguous requirement into a working, tested product, into something measurably faster or more reliable than a single agent operating at the same token budget. Secondary contributions include a reusable, presentation-agnostic event-log architecture for multi-agent system observability, and an applied instance of the MAST failure taxonomy against a concrete, non-trivial multi-agent workload.
