Log

23/09/2026Foundational design session

Started from the supervisor's original pitch — a multi-agent LLM system mimicking a software company — and the project brief document brought to the first working session. Confirmed the pre-existing decisions: five agents across three tiers (CTO / Product / 3× Engineering), a single code path for attaching to or creating a repository, Slack-style channel-based communication rather than a free-for-all chat, and a presentation-agnostic event log underneath whatever visualisation gets built. Explicitly rejected a pixel-art "walk around the office" visualisation as premature.

Designed the communication protocol from four open questions (message format, routing, turn-taking, context passing): landed on a unified typed Message record that doubles as the event log, orchestrator-mediated publish/subscribe routing (rejecting both direct agent-to-agent calls and a fully autonomous reactive task board), a per-ticket finite state machine for turn-taking, and structured handoff notes instead of full chat-history replay for context passing.

Designed the execution sandbox: one Docker container per ticket-attempt, torn down after each attempt, with a fixed tool interface (run_tests, run_command, file read/write, git diff/commit) rather than raw shell access.

Follow-up pass surfaced two gaps and closed them: a persistent per-run git workspace beneath the ephemeral sandbox containers (git history must outlive any single attempt), and isolating hidden acceptance tests from the agent-visible test runner to preserve evaluation validity. Also confirmed: retry cap of 3 before escalation, strictly sequential one-ticket-at-a-time concurrency, a CTO-then-Product requirement intake pipeline, git branch-per-ticket with the Review→Done transition acting as the actual merge, and SQLite over Postgres for the event log/task board.

23/09/2026Interface direction

Decided observation needed to be live, not just after-the-fact log inspection — this pushed the design toward a websocket-driven dashboard rather than a static export. Settled on a minimal default view (chat feed) with additional detail gated behind a settings panel, split into two independent toggle groups once it became clear the interface serves two different purposes at once: showcasing the multi-agent "society" dynamics for the viva, and surfacing technical metrics for debugging/evaluation. Both groups render from the same underlying message stream.

25/09/2026Scope check against the submitted Project Definition Form

Compared the working design against the CS3IP Project Definition Form as actually submitted to Ziyang (dated 24/09/2026) and found four real divergences, plus one softer emphasis mismatch. In every one of the four hard clashes, the form turned out to be correct and the working design had drifted away from it — not the reverse — so the design was updated to match the form rather than the form being changed:

  • Channels: form specifies role- and feature-based channels; design had settled on ticket-based only. Resolved by making grouping strategy (role/feature/ticket) a user-selectable option rather than one hardcoded default.
  • Custom roles & personalities: form promises a user-facing feature; design only had internal developer-facing config. Promoted to a real v1 feature.
  • Kanban board: form commits to it as one of two built-in views; design had dropped it in favour of a single dashboard. Added back in as a second tab, drilling down into a ticket's message thread on click.
  • Observe and intervene: form frames both as deliverable; design had explicitly backlogged intervention. Promoted to a real v1 feature — gated at the Review and Escalated ticket states, surfaced as controls directly on kanban cards.

The unresolved fifth point: the form states "formal repeated experiments are not the core deliverable," while the evaluation design (hidden-test benchmarking, a MAST-based failure taxonomy, baseline comparison) reads as fairly rigorous. Not a contradiction on its face, but an emphasis question worth Ziyang's input rather than a unilateral call — see the next entry.

A standalone alignment-notes document was produced recording all five points for Waleed's own reference when updating the form later; the form itself was not touched.

25/09/2026Implementation begins — Layer 1

Started scaffolding the WJ-FYP repository. Layer 1: the core Pydantic data models (Message, Ticket, Channel, RoleConfig) and the declarative ticket finite-state-machine transition table. Checked each model against the same-day form-alignment scope changes before moving on: the generic Message/Ticket/Channel schemas needed no changes, since they were already designed to not assume any one channel-grouping strategy or presentation layer. Two did need revisiting — RoleConfig gained a personality field and an is_preset flag to support user-created custom roles, and the FSM gained a requires_approval flag on transitions to support the newly-promoted human intervention feature, set on exactly the four transitions matching where intervention controls live on the kanban board (Review→Done, Review→In Progress, Escalated→In Progress, Escalated→Halted).

25/09/2026Comprehensive project brief produced

Compiled the full technical design into a single detailed brief document — architecture, communication protocol, sandbox, dashboard, evaluation methodology, technology stack, constraints, and expected contribution — intended both as standalone documentation and as the source material for a future project poster. Added a Related Work section engaging with three papers Ziyang assigned as background reading (Generative Agents, Agent Hospital, Agent Laboratory), plus verified citations for the three evaluation-methodology papers already informing the design (MAST, TheAgentCompany, SWE-bench).

25/09/2026Implementation continues — Layer 2

Config layer: config/roles.yaml (the preset three-tier team as data, model names left as placeholders pending API budget confirmation), config/settings.yaml (retry cap, concurrency mode, autonomy mode, event log backend — all previously confirmed decisions now expressed as actual config rather than only design notes), a loader module connecting both to the Layer 1 models, and a pyproject.toml declaring dependencies without installing anything, since the dev environment remains intentionally parked.

25/09/2026Deep-dive research on cited papers and comparable tools

Ran two research passes to go beyond abstract-level understanding of the papers already cited, and to check the design against existing multi-agent/coding-agent tools (ChatDev, MetaGPT, AutoGen, CrewAI, OpenHands, SWE-agent, Devin).

Paper deep-dive surfaced several concrete, adoptable mechanisms: MAST's exact 14-code failure taxonomy (our "context lost at handoff" concept maps precisely to code FM-1.4), SWE-bench's exact FAIL_TO_PASS/PASS_TO_PASS test-pair mechanism, TheAgentCompany's weighted partial-credit scoring formula, Generative Agents' recency/importance/relevance memory-scoring formula as a candidate improvement to the on-demand history tool, and Agent Laboratory's three-option (not binary) human checkpoint. It also surfaced that TheAgentCompany's benchmark requires standing up its full GitLab/Plane/RocketChat/ownCloud service stack — heavier infrastructure than the brief had assumed, and now an open decision rather than a settled one.

Comparable-tools research found that several already-made design choices are independently validated by existing systems (MetaGPT's pub-sub message pool, SWE-agent's constrained tool interface, OpenHands' append-only event log), and found documented pitfalls in those same tools that justify stricter choices already made here — most notably MetaGPT's own failure analysis attributing 43% of its code-inconsistency failures to agents ignoring prescribed context, directly validating the decision to make handoff notes mandatory rather than optional.
